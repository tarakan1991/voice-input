## Разобранные инциденты

**Windows: нулевые DLL llama в target и в инсталлере (этап 6).**
Симптом: после `tauri build` llama.dll/ggml*.dll в `target/release` и в
NSIS-инсталлере имели размер 0 байт, вычитка не работала.
Причина: цепочка из трёх фактов. (1) build-скрипт voice-input не зависит от
llama-cpp-sys-2 и может выполниться раньше него; (2) он создавал пустые
плейсхолдеры DLL в `frameworks/` (по образцу macOS, где tauri_build требует
существования bundle.macOS.frameworks на этапе компиляции); (3) tauri_build
на Windows копирует ресурсы (`frameworks/*.dll`) в `target/<profile>`, а
llama-cpp-sys-2 хардлинкает свои DLL «только если файла ещё нет» — пустышка
занимала имя, и настоящая DLL не появлялась.
Решение: на Windows каталог frameworks/ и bundle.resources не используются
вовсе — DLL кладёт в `$INSTDIR` NSIS-хук (`File "..\..\<имя>.dll"` из
`target/release`, где их создают сборки llama-cpp-sys-2 и ort-sys), удаление
— в PREUNINSTALL-хуке. macOS-путь не менялся.

**Windows: краш 0x80000003 при загрузке модели в debug-сборке (этап 6).**
Симптом: `cargo test asr_smoke` (debug) падал внутри whisper_model_load;
в release тот же тест проходит.
Причина: llama-cpp-sys-2 в debug-профиле линкует отладочный CRT
(msvcrtd → ucrtbased), а C++-код whisper.cpp/llama.cpp собран с /MD
(release CRT). Две кучи в одном процессе → heap mismatch → int3.
Решение: на Windows диктовка и смоуки проверяются в release
(`cargo tauri dev --release`, `cargo test --release ... -- --ignored`);
юнит-тесты CI не трогают нативные модели и на debug не страдают.
Зафиксировано в CLAUDE.md (Dev-заметки Windows).

**Windows: клик по кнопке ✕ не доходил до WebView2 (этап 6, риск R-1).**
Симптом: неактивирующийся оверлей работал (фокус не крадётся), но клик по
кнопке ✕ не отменял диктовку — JS-обработчик onclick не срабатывал.
Причина: дочерние HWND WebView2 принадлежат процессам msedgewebview2.exe.
Сабклассинг их из нашего процесса невозможен (SetWindowSubclass кросс-
процессно молча не ставится), а сам WebView2 в окне с WS_EX_NOACTIVATE/
MA_NOACTIVATE не доводит нажатие до DOM.
Решение: на время видимости оверлея ставится низкоуровневый мышиный хук
(WH_MOUSE_LL); отпускание левой кнопки над некликнасквозь-окном оверлея
превращается в событие `overlay-native-click` (константа платформенной
границы), которое слушает общий код (overlay_ctl) и отменяет диктовку.
Плашку хук не трогает: она WS_EX_TRANSPARENT, и WindowFromPoint её
пропускает — клики «сквозь» неё уходят приложению под ней. Вне записи хук
снят и на клики в системе не влияет.
Попутно: скрытое главное окно активировалось при старте (WebView2 фокусирует
хост при создании) — вылечено `"focus": false` в tauri.conf.json; окно
кнопки 32×32 Windows раздувал до минимальной ширины ~136px — размер
переустанавливается при показе.

**Windows: стоп хоткеем без речи гонял Whisper по тишине (этап 6).**
Симптом: случайный двойной хоткей давал минуты «обрабатываю» на CPU.
Причина: SPEC §4.4 требует «речи не было вообще → Idle без обработки», но
это было реализовано только для автостопа по тишине; остановка хоткеем
отправляла запись в ASR даже при нуле речевых окон VAD.
Решение: любой Process-стоп без единого речевого окна трактуется как
NoSpeech (общий код, session.rs) — честное «Речи не слышно» вместо прогона
модели по тишине. На macOS эффект тот же, просто цена ошибки была ниже.

**Пустое распознавание на Metal (найдено при первой живой проверке).**
Симптом: модель скачивалась и проходила SHA256, но тестовый прогон и живая
диктовка возвращали пустой текст; на CPU (`VOICE_INPUT_NO_GPU=1`) всё работало.
Причина: whisper-rs и llama-cpp-2 статически линковали РАЗНЫЕ копии ggml —
линкер оставлял одну, whisper вызывал чужой Metal-бэкенд с несовместимым ABI
и получал NaN-логиты (декодер мгновенно завершал сегмент без текста).
Диагноз подтверждён: whisper.cpp 1.7.4 печатал лог-строки, существующие только
в новом ggml от llama.cpp. Решение: llama-cpp-2 собирается с `dynamic-link`
(dylib в Contents/Frameworks, rpath в build.rs) — two-level namespace macOS
изолирует символы. Оба смоук-теста зелёные (`asr_smoke`, `llm_smoke`).
Для Windows-этапа зафиксирован риск R-13 в SPEC.md.

## Известные ограничения v1 (осознанные, SPEC.md §11, §15)

- Менеджеры буфера обмена видят транзитный вставляемый текст.
- Поля защищённого ввода (пароли): вставка блокируется, текст остаётся
  в буфере, показывается уведомление.
- Детект «хоткей занят» видит только конфликты глобальных хоткеев, не
  внутренних шорткатов приложений.
- Dev-сборки без стабильной подписи теряют TCC-права при пересборке
  (процедура с самоподписанным сертификатом — CLAUDE.md).
